Theming here is a stylesheet, not a runtime. The Tecton theme ships as `tokens.css`: every design token is a CSS custom property, declared once on the document, with light and dark values. Elements read those properties through the cascade, so a change to a token on any ancestor reaches every element below it, and the browser resolves light and dark natively.

:::note[What exists today]
The token stylesheet, its light, dark and inverted-surface blocks, the token metadata (`tokens.js`, `tokens.json`), the `tct-theme` and `tct-media-theme` elements and the `defineTheme` family of utilities in `@tecton-astryx/core` all exist. One limitation: the `theme` property of `tct-theme` still selects a theme by name only, so a theme made with `defineTheme` is applied by loading its generated CSS yourself (see [Loading themes for production](#loading-themes-for-production)). `tct-syntax-theme` is _planned_. The attribute-based mechanism (`data-theme`, `data-media-theme`) works with the stylesheet alone.
:::

## Quick start

Load the stylesheet once, in the document, and you have the Tecton theme:

```css title="global.css"
@import '@tecton-astryx/tokens/tecton.css';
```

That is the whole setup. The page follows the operating system's light or dark preference by default, because the stylesheet sets `color-scheme: light dark` on the root. The same file is valid for a server-rendered page, a static page and a single-page app, and the tokens are present at first paint. (If you also use the elements, import `@tecton-astryx/components/tecton.css` instead: it adds the styles they need. See [Installation](../installation/#stylesheets-and-fonts).)

To scope a theme to part of a page, use an element that switches the scheme (see [Nesting themes](#nesting-themes)).

## Available themes

Tecton is the theme this library ships. It has a designed light and a designed dark mode. Its values come from the Tecton design-system export, with the owner's Tecton theme bindings used for the roles the export does not define (see [Color](../color/)). There are no alternative theme packages.

Each token in the metadata carries a status, so you know where a value came from:

| Status             | Meaning                                                                                                |
| ------------------ | ------------------------------------------------------------------------------------------------------ |
| Tecton             | From the Tecton export. Authoritative for role values in both modes.                                    |
| Tecton (bound)     | From the owner's Tecton theme bindings, for roles the export does not define.                          |
| default            | A default that Tecton deliberately keeps (spacing, three tiny font sizes).                             |
| retained default   | Kept on purpose because Tecton has no value (the ten motion tokens).                                   |
| provisional        | No Tecton decision yet: a proposal (56 data-visualisation colours, `--size-element-lg`, some extras).  |

The [design tokens reference](/reference/tokens/) shows the status of every token.

## The theme element

`tct-theme` scopes a colour mode, and a theme name, to its subtree. It has no shadow root: its children stay in your tree.

| Attribute or property | Type                              | Default    | Description                                                                                       |
| --------------------- | --------------------------------- | ---------- | ------------------------------------------------------------------------------------------------- |
| `mode`                | `system`, `light` or `dark`       | `system`   | Colour mode, reflected. `system` follows the operating system, including changes while the page is open. |
| `theme`               | A theme name, or an object with a `name` | `tecton` | The theme's name, reflected as `data-tct-theme` (the scope of generated theme CSS). Only the name is used: a `defineTheme` object is not applied by the element yet. |

Unlike most providers, it is not `display: contents`: the host is a block that pins `color-scheme` and paints the page surface and text colour, which is what makes a scheme island render correctly (see [Nesting themes](#nesting-themes)). It publishes its name and resolved mode (`light` or `dark`, never `system`) to the elements inside it.

The outermost `tct-theme` on a page also keeps `<html data-theme>` and `<html data-tct-theme>` in step, so the viewport, scrollbars, native controls and layers in the top layer follow the mode. Nested themes are islands only, and they never touch the page.

```html
<tct-theme mode="dark">
  <tct-text>Always dark, whatever the page does</tct-text>
</tct-theme>
```

Persist the user's choice yourself and set `mode` from it. Add `<meta name="color-scheme" content="light dark">` to the head, and set `<html data-theme>` on the server if you want to avoid any flash before scripts run. See the [`tct-theme` page](/components/utility/theme/) for the full reference.

## Creating a custom theme

There are two routes. Use the first for a handful of overrides, the second for a reusable, generated theme.

### Override tokens in CSS

Tokens are unregistered custom properties declared with zero specificity (`:where(:root)`) inside `@layer tecton.tokens`. Any of your own rules, layered or not, override a token without `!important`. Override the semantic token, not the component:

```css title="brand.css"
:root {
  /* a non-colour token: one value for both modes */
  --radius-container: 12px;

  /* a colour token re-pointed at another Tecton token; the target still switches with the mode */
  --color-border: var(--tecton-color-divider-strong);
}
```

Use Tecton tokens for colour values, not literals. When you need a colour that no token expresses, use the opt-in palette (`@tecton-astryx/tokens/palette.css`, which defines `--tecton-palette-<hue>-<surface>-<stop>`, for example `--tecton-palette-mauve-on-light-680`) rather than a hex value, so your override stays inside the Tecton system.

Two rules keep overrides predictable:

- **Token names are global.** There is one `tokens.css` per page, supplied by the host application. Do not load two copies.
- **Do not register token properties as `<color>`.** Tokens hold a `light-dark()` expression that must stay live so that descendants re-resolve under their own `color-scheme`. A registered `<color>` custom property resolves at computed-value time and freezes the ancestor's choice.

### `defineTheme`

`defineTheme` (exported from `@tecton-astryx/core`) creates a theme from token overrides and optional scale configurations, and `generateThemeCSS` turns it into a stylesheet that uses this library's token names. The theme is registered under its `name`, which is the value of the `data-tct-theme` attribute. Explicit `tokens` always take precedence over scale-generated values, token by token, and only the tokens you list are written: everything else keeps its default from `tokens.css`.

```js
import {defineTheme, generateThemeCSS} from '@tecton-astryx/core';

const brandTheme = defineTheme({
  name: 'brand',
  tokens: {
    // [light, dark] tuples for colour tokens, one value otherwise
    '--color-accent': ['#0064e0', '#48cae4'],
    '--radius-element': '6px',
  },
});

const {component, prose} = generateThemeCSS(brandTheme); // two CSS strings, see below
```

The configuration axes map onto this library as follows:

| Config             | Generates                                                                | In this library                                                                                                                  |
| ------------------ | ------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| `color`            | `--color-accent`, `--color-background-*`, `--color-text-*`, `--color-border` and so on, from an accent seed | Tecton's own colours are explicit role values from the export, not derived from a seed. Use `color` for a new theme; override tokens to adjust Tecton |
| `typography.scale` | `--text-*-size`, `--text-*-weight`, `--text-*-leading`                    | Tecton's scale is a fixed ladder (10, 12, 14, 16, 20, 24, 32, 40, 48 px), not geometric, so Tecton writes it as explicit tokens   |
| `typography.*`     | `--font-family-body`, `--font-family-heading`, `--font-family-code`       | Figtree and IBM Plex Mono; changing the family is an override of these tokens. Loading the fonts stays your job                  |
| `radius`           | `--radius-inner`, `--radius-element`, `--radius-container`, `--radius-page`, `--radius-chat` | Tecton values 2, 4, 8, 16 and 12 px                                                                                       |
| `motion`           | `--duration-*`, `--ease-standard`                                         | Retained defaults                                                                                                                |

`localTokens`, `icons`, `indicators`, `syntax`, `onDark`, `onLight` and `components` are the other inputs; the sections below cover the ones you will use most.

## Extending a theme

`extends` derives a new theme from an existing `defineTheme` result, inheriting its tokens, component overrides, icons, indicators, media-surface overrides and adaptations. Only specify what you want to change; the base has the lowest precedence. Inheritance is resolved when the theme is defined, so an extended theme is flat: its generated stylesheet is self-contained and the base theme's CSS does not need to be loaded next to it. Passing something that is not a defined theme throws.

```js
const brandDense = defineTheme({
  name: 'brand-dense',
  extends: brandTheme,
  tokens: {'--size-element-md': '28px'},
});
```

## Theme adaptations

Adaptations are opt-in token and component changes under a viewport width, primary-pointer precision, contrast preference or motion preference, given to `defineTheme` as `adaptations.rules`. Conditions in one rule (`when`) are combined with AND, rules apply in order, and later matching rules win.

| Condition                    | Values                                |
| ---------------------------- | ------------------------------------- |
| `width.from` and `width.below` | `sm`, `md`, `lg`, `xl`, `2xl`       |
| `pointer`                    | `coarse` or `fine`                    |
| `contrast`                   | `more`, `less` or `no-preference`     |
| `motion`                     | `reduce` or `no-preference`           |

The named widths are retained defaults, because Tecton has none: `sm` 640, `md` 768, `lg` 1024, `xl` 1280, `2xl` 1536 CSS pixels (`adaptations.widthBreakpoints` overrides them); `from` includes its point and `below` excludes it. Adaptations compile to CSS media queries, so there is no resize listener and no re-render.

```js
defineTheme({
  name: 'brand-touch',
  extends: brandTheme,
  adaptations: {
    rules: [{when: {pointer: 'coarse'}, value: {tokens: {'--size-element-md': '40px'}}}],
  },
});
```

You can write the same thing by hand without `defineTheme`:

```css
/* coarse pointers get larger controls */
@media (pointer: coarse) {
  :root {
    --size-element-sm: 36px;
    --size-element-md: 40px;
    --size-element-lg: 44px;
  }
}
```

`prefers-contrast: more` is not handled by the elements in version 1, so a `contrast` adaptation is the way to add it for your product. Forced-colours mode is required and handled: the stylesheet maps roles to system colours (`Canvas`, `CanvasText`, `ButtonBorder`, `Highlight`, `LinkText`, `GrayText`) under `@media (forced-colors: active)`.

## Component style overrides

Component-level overrides go through the public styling surface, in order of preference: tokens, attributes, `::part()`, `:state()`, documented component custom properties, and `::slotted()`. See [Styling components](../styling/).

```css
/* an override through a documented component custom property */
tct-button {
  --button-focus-offset: 3px;
}

/* an override through an anatomy part */
tct-button[variant='ghost']::part(button) {
  border-width: 2px;
  border-style: solid;
}
```

Prefer re-pointing the token an element already reads over setting a property on it. Setting the property directly bypasses the state and hover mixing that the element does from tokens, and it can defeat forced-colours handling. The names of the public custom properties and parts are listed on each element's page, and private properties (those that start with `--_`) are not an API.

`defineTheme` also takes a `components` map for the same intent: each key is a component name (`button`, `banner`, ...), and its values map a style key to CSS properties. The key `base` styles every instance, and `prop:value` (or `prop:value+prop:value`) selects on the reflected attribute of the host, with pseudo-classes such as `:hover` nested inside. The generator resolves each key to the element's tag and part (`tct-button::part(button)`).

```js
defineTheme({
  name: 'brand',
  components: {
    button: {
      base: {fontWeight: '600'},
      'variant:secondary': {backgroundColor: 'var(--color-background-muted)'},
    },
  },
});
```

A theme family (one keyed bundle holding several themes) has no equivalent here, because a page loads one stylesheet.

## Custom variants

Elements validate an enumerated attribute against its documented list: an unknown value falls back to the default and warns once in development (`globalThis.tctDevMode = true`). A `prop:value` key in a theme's `components` map only matches when an element carries that attribute value, so a theme cannot add a variant to an element it does not own. The values Tecton adds to the standard lists (the `outlined` and `text-only` button variants, for example) are part of the elements and documented on their pages.

## Loading themes for production

Load the stylesheet, not a script. A static stylesheet is present at first paint, before any JavaScript runs, so there is no flash of unthemed content, and it works for server rendering. For a custom theme, generate its CSS at build time with `generateThemeCSS` and load it after `tokens.css`, or write the overrides by hand in your own stylesheet.

`generateThemeCSS(theme)` returns two strings. `prose` holds the theme's defaults for bare HTML elements and belongs in `@layer tecton.reset`, so any class wins over it. `component` holds the token and component overrides and belongs in a layer that follows `tecton.tokens` (such as `tecton.light-dom` or a layer of your own declared after it), so the theme wins over the defaults. Both are scoped to `[data-tct-theme="<name>"]` with `@scope`, so put `data-tct-theme` on the element that should take the theme, or on an outermost `tct-theme` with `theme="<name>"`. `@scope` is in current Chromium and Safari releases (Chrome 143, Safari 26.4) but not yet in every Tier 1 engine, so a generated theme is a progressive enhancement until it is; the hand-written token overrides above work everywhere.

| Concern                        | Static stylesheet (recommended)                | JavaScript-injected styles                        |
| ------------------------------ | ---------------------------------------------- | ------------------------------------------------- |
| First paint                    | Tokens present                                 | Tokens arrive after script                        |
| Server rendering               | Fully supported                                | Flash on hydration                                |
| Best for                       | Production                                     | Prototyping only                                  |

If you cannot avoid a script, you can still adopt a stylesheet you generated in the document with `document.adoptedStyleSheets`, but the first-paint caveat stays.

## Light and dark mode

By default the page follows the operating system. `color-scheme: light dark` is set on the root, so native controls, scrollbars and the canvas follow too, and every colour token resolves through `light-dark()`. Where a browser lacks `light-dark()` (Chrome 116 to 122, Safari 17.0 to 17.4), the stylesheet falls back to a `prefers-color-scheme` media query for the same values.

To let people choose a mode, set `data-theme` on `<html>` (or use the outermost `tct-theme`, which does it for you). `data-theme="light"` and `data-theme="dark"` pin a mode, and removing the attribute returns to the system preference.

The default must stay the system preference, and the page should still work if your script fails. Offer a two-state control: the system setting, and the opposite of it. Selecting the opposite pins that exact scheme, so it does not flip if the system setting changes later. Persist the choice in `localStorage`, and apply it before first paint with a classic inline script in the head (not `type="module"`, not `defer`), so a pinned preference does not flash:

```html
<meta name="color-scheme" content="light dark" />
<script>
  {
    const scheme = localStorage.getItem('color-scheme'); // 'light' | 'dark' | null
    if (scheme) {
      document.documentElement.dataset.theme = scheme;
      document.querySelector('meta[name="color-scheme"]').content = scheme;
    }
  }
</script>
```

```js title="the toggle"
const root = document.documentElement;
const systemDark = matchMedia('(prefers-color-scheme: dark)');

function pin(scheme) {
  root.dataset.theme = scheme;
  document.querySelector('meta[name="color-scheme"]').content = scheme;
  try {
    localStorage.setItem('color-scheme', scheme);
  } catch {
    // Private windows can refuse storage; the pin then lasts for this page load only.
  }
}

// "the opposite of the system setting" is chosen once, when the user clicks
button.addEventListener('click', () => pin(systemDark.matches ? 'light' : 'dark'));
```

`tct-theme` offers `system`, `light` and `dark` as its API so that a design tool or a settings page can express all three, but the recommended interface for end users is the two-state control above.

## Nesting themes

An element that switches the colour scheme (`data-theme`, or `tct-theme`) creates a scheme island. Because tokens use `light-dark()` and are unregistered, a dark island inside a light page inside a dark page resolves correctly: `color-scheme` inherits and each token re-resolves where it is used.

The stylesheet gives every `[data-theme]` element what an island needs, following the rule that an element which switches scheme must also set its own background and re-specify inherited colours:

```css
/* from tokens.css, abbreviated */
:where([data-theme='dark']) {
  color-scheme: dark;
  background-color: var(--color-background-body);
  color: var(--color-text-primary);
  accent-color: var(--color-accent);
}
```

Without that, text would keep the ancestor's already-resolved colour on a background of the wrong scheme. In browsers without `light-dark()` only one level of `[data-theme]` island is reliable in the fallback path, which is an acceptable degradation.

### Content over media

`data-media-theme="dark"` and `data-media-theme="light"` pin the dark or light side of each colour pair for content that sits on an image or a coloured surface. They set the primary and secondary text colours, the surface, border, icon and accent colours. The `tct-media-theme` element sets the attribute for you and adds a `mode`: `dark` or `light` to pin a side, `auto` (the default) to measure the surface that was painted and decide, and `off` to remove the context. `fallback` (`dark` or `light`) is the side `auto` uses while it cannot measure, for example over a background image. It has no box and paints no background: put the background on the parent, and use it for local surface inversions, not for the page's colour mode.

Focus ring: the ring is Tecton hot pink everywhere, and pink fails the 3:1 non-text contrast on inverted surfaces. On those surfaces the ring gains a second, inner ring (`--tecton-color-focus-inner`) in the surface's contrast colour, and `tct-media-theme` moves the ring with the side. `--tecton-color-focus-inner` is _provisional_: it is a proposal, not a Tecton value.

### Overlays

Menus, popovers, dialogs and toasts stay in their place in the DOM and use the top layer, so they inherit tokens, `dir` and `lang` from where they were opened. A dialog opened from inside a dark island is dark.

## Reading the theme from JavaScript

Prefer CSS variables for ordinary styling. When JavaScript needs a value (a canvas, a chart library, a map style), use the metadata module or read the computed style.

```js title="Token metadata"
import {tokens, tokenVar, breakpoints} from '@tecton-astryx/tokens/tokens.js';

tokens['--color-text-primary'].light; // '#21172a'
tokens['--color-text-primary'].dark; // '#f6f5f8'
tokens['--color-text-primary'].status; // where the value came from (the statuses above)

tokenVar('--spacing-4'); // 'var(--spacing-4)'
breakpoints.values.md; // 768
```

The module is metadata for docs and tools. It does not track your overrides or a nested island; runtime styling always uses `tokens.css`.

To get the value at a specific place in the page, let the browser resolve it. A custom property that holds `light-dark()` is returned as text, not as a colour, so paint it onto a property and read that:

```js
function resolvedColor(element, token) {
  const probe = document.createElement('span');
  probe.style.color = `var(${token})`;
  element.append(probe);
  const value = getComputedStyle(probe).color;
  probe.remove();
  return value; // 'rgb(33, 23, 42)' in light mode
}
```

For a theme made with `defineTheme`, `resolveThemeTokens(theme, {mode})` returns every token as a concrete value for `light` or `dark`, following `var()` references and `color-mix()`, and `resolveThemeToken(theme, name, {mode})` returns one. `registerTheme` and `getRegisteredTheme(name)` look themes up by name. Elements read the name and resolved mode of the nearest `tct-theme` through the theme context (`themeContext` in `@tecton-astryx/core/context/keys.js`). A token-reading controller for element authors is _planned_.
