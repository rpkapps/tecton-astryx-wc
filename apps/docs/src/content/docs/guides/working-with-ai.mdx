## Overview

The design system is built to be AI-friendly: consistent naming, predictable attribute patterns (see [React to Web Components](../react-to-web-components/) for the rules), and structured documentation that can be fed directly into an AI context window. But models still need the right context to avoid falling back to generic HTML or React patterns, or inventing attributes.

The surface is:

| Capability                 | What it is                                                                                                                                                                  | Status    |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------- |
| Agent metadata per element | `keywords` (the search index), a dense doc (one-line description, dense usage, do and don't best practices, one-line attribute descriptions) and related elements            | Available |
| `llms.txt`                 | An index for language models, plus `llms-full.txt` (everything in one file) and a JSON registry, all generated from the manifest and the docs                                | Available |
| The `tct` CLI              | `component`, `docs`, `search`, `discover`, `controllers`, `doctor`, `gap-report`, `layout`, `init --features agents`, `upgrade`, `mcp` and `manifest`, in the private `@tecton-wc/cli` package | Available |
| Output modes               | `--dense` (token-efficient) and `--json` (a stable envelope) on the commands that print data; `--detail brief\|compact\|full` on lists                                       | Available |
| MCP server                 | `search(query)` and `get(name)`, as `tct mcp` over stdio, and live over HTTP at `/mcp` on the docs site (served by a Node process)                                                          | Available |
| Agent-eval harness         | Fixture prompts that check an agent produces correct `tct-*` code given the agent docs (internal)                                                                            | Planned   |

## Quick start

Install `@tecton-wc/cli` next to `@tecton-wc/components` (both are private packages: use the workspace, tarball or Git source your team uses), then ask your AI to set itself up:

```text title="Paste this into your AI"
Run `npx --no-install tct init --features agents` in this project to set up your Tecton context, then read the generated file. Before you write any UI, follow its workflow.
```

Or run it yourself:

```bash
npx --no-install tct init --features agents
```

```text
[ok] Agent docs installed -> AGENTS.md
```

The command generates everything your AI needs from the packages installed in the project: an element index, behavioural rules and a CLI reference. It writes them between `<!-- TCT:START -->` and `<!-- TCT:END -->` markers, so text you write in the same file is never touched. When no agent-doc file exists it creates `AGENTS.md`, the tool-agnostic standard that most agents read; when some do, it refreshes each of them.

After a dependency bump, `tct upgrade` reports a stale block and `tct upgrade --apply` refreshes it. It never overwrites a block you edited by hand unless you add `--force`, and it never writes outside the markers:

```text
$ tct upgrade
Agent docs need attention

AGENTS.md          stale (older than the installed registry) - 0.0.0
.claude/CLAUDE.md  up to date - 0.0.0

Run `tct upgrade --apply` to refresh stale blocks (text outside the markers is never touched).
```

`tct upgrade --check` exits 1 when any block is stale, edited or malformed, so it works as a CI gate. Without any agent-doc file, point your AI at the files the site already publishes instead: [llms.txt](/llms.txt) is a short index of the guides and elements, [llms-full.txt](/llms-full.txt) holds their full text, and the [registry](/agent-registry.json) has one entry per element with its tag, attributes, slots, events, dense usage, best practices and examples.

To target one tool's file instead of the default:

```bash title="One tool"
tct init --features agents --agent claude    # .claude/CLAUDE.md
tct init --features agents --agent cursor    # .cursorrules
tct init --features agents --agent codex     # AGENTS.md (Copilot, Codex and others)
tct init --features agents --agent all       # all of the above
tct init --features agents --agent-docs-path docs/ai/tct.md   # any file inside the project
tct init --remove-agents                     # remove the managed block again
```

`--agent-docs-path` takes a path relative to the project (it is repeatable). Absolute paths, paths that leave the project and links that point outside it are refused, and every target is checked before the first one is written. `tct init --dry-run` prints the block without writing anything.

## What gets generated

The generated context teaches your AI a workflow before it writes any UI code:

1. `tct search "<what you need>"`: find the right element, controller or doc topic.
2. `tct component <tag> --dense`: read attributes, slots, events and examples for every element you use.
3. `tct docs <topic>`: read the guide for the pattern you are building (layout, forms, theming, accessibility).

Page templates are not part of the workflow yet.

The block also includes rules that prevent common mistakes, a CLI quick reference, and an index of every element grouped by category. The rules are the ones on the [Principles](../principles/) page, stated for agents. You can give them to any AI tool by hand:

- Use `tct-*` elements before raw HTML for what they cover, and register the families you use (`import '@tecton-wc/components/button'`).
- No inline `style` on raw wrappers; use the layout elements, tokens, attributes, `::part()` and custom properties.
- No hardcoded colours or spacing; use `var(--color-*)` and `var(--spacing-*)`.
- Never invent attributes, slots or events; read the element's page first.
- Icon-only buttons need a `label`. Form controls need a `label` and a `name`.
- Use `tct-link` for navigation, and real `<form>` elements for forms.
- Set structured data as properties (`items`, and the like), never as JSON attributes.

After setup, you should not need to correct your AI on these conventions by hand; the agent docs handle it at the system level. The block names the way to run the CLI that fits the project: the `tct` script when `package.json` has one (`pnpm tct`, `npm run tct --` or `yarn tct`, by the lockfile), otherwise `npx --no-install tct`.

## Cursor setup

Cursor project rules are not always picked up: Cursor chooses which rules to apply by relevance. For reliable inclusion, install the design system context as a user rule instead. User rules live in `~/.cursor/rules/` and apply across all projects. Because `--agent-docs-path` must stay inside the directory you run the command in, run it from your home directory and point it at the registry of a project that has the packages installed:

```bash title="Install as a Cursor user rule"
cd ~
tct init --features agents \
  --registry ~/code/my-app/node_modules/@tecton-wc/components/agent-registry.json \
  --agent-docs-path .cursor/rules/tct.mdc
```

Files ending in `.mdc` get the front matter Cursor reads (`alwaysApply: true`), so the rule is always in context.

## Checking your setup

Paste this into your AI before it writes any element code. Models tend to answer these three questions confidently and wrongly without the docs. If your AI cannot answer them, it will know to read the docs first.

```text title="Paste this into your AI"
Before writing any Tecton code, check your knowledge:

1. What import registers the button element?
2. How do you make a dialog non-dismissible?
3. Which property does the tree list use for its items?

If you don't know all three, run `tct search` and `tct component <tag> --dense` (or read /llms.txt) before you continue.
```

The answers the docs give: `import '@tecton-wc/components/button'` (which registers `tct-button`); `purpose="required"` on `tct-dialog`, which blocks Escape, backdrop and close-button dismissal; and the `items` property on `tct-tree-list` (structured data is a property, never an attribute).

`tct doctor` checks the setup itself: the Node version, the registry, whether `@tecton-wc/components` is installed and in step with the CLI, whether the stylesheet is loaded, unknown `tct-*` tags in your sources and the freshness of the agent docs. It is read-only, so it is safe in CI.

## The `tct` pattern

AI agents frequently invoke a CLI with a guessed path or a different package's binary, which fails silently. Give them one stable command by adding an npm script alias:

```json title="package.json"
"scripts": {
  "tct": "tct"
}
```

With this alias, agents run `pnpm tct component tct-dialog --dense` (or `npm run tct -- component tct-dialog --dense`) instead of guessing. The `--` separator is the standard npm convention for passing flags to scripts.

The package is not on a public registry, so a bare `npx tct` can resolve to an unrelated package until the CLI is installed as a dependency. Prefer the script alias, or `npx --no-install tct` to refuse any download.

```bash title="Reliable CLI invocation"
pnpm tct component
pnpm tct component tct-dialog --dense
pnpm tct docs styling --dense
pnpm tct docs tokens --dense
```

## The `--dense` flag

Commands that print element and guide content support `--dense`, a token-efficient format designed for AI context windows. Use it when pasting CLI output into a web-based AI tool. Dense output comes from the dense doc that each element authors (a one-line description, dense usage, best practices as do and don't, and one line per attribute, slot and event), so it is short by design, and the build checks it against the element's real API so that it cannot omit a public member. The same dense docs are in the registry, under each element's `dense` key.

```bash title="Dense output for pasting into AI conversations"
tct component tct-dialog --dense
tct docs styling --dense
tct docs tokens --dense
```

```text
$ tct component tct-dialog --dense
tct-dialog, tct-dialog-header (Overlay)  import '@tecton-wc/components/dialog'
modal overlay on native dialog that blocks page interaction until the user responds; purposes, nesting, focus return, openDialog()
usage: Displays a modal that blocks the page. Use it for delete confirmations, edit forms and terms acceptance. ...
+ Choose the right purpose: info for dismissable content, form to prevent accidental backdrop dismissal, required when the user must respond.
- Use a dialog for simple messages that could be inline or a toast.
api:
  open: whether the dialog is open; the attribute opens it initially; writing it never emits an event
  purpose: what may dismiss it (required nothing, form Escape only, info Escape and the backdrop); default info
  ...
```

On lists, `--detail brief|compact|full` trades size for content: names only, names with one-line descriptions, or full docs per entry.

## The `--json` flag

Every command that prints data also supports `--json`, a stable machine-readable envelope, for tools and scripts. A response has an `apiVersion`, a `type` (such as `search` or `component.detail`), `data` and sometimes `meta`; an error has an `apiVersion`, a human-readable `error`, a stable `code` and optional `suggestions`. Branch on `code`, never on the message, because codes are append-only and messages change freely. Errors exit 1, and in `--json` mode nothing is written to stderr.

```text
$ tct component tct-buttn --json
{
  "apiVersion": 1,
  "error": "No element named \"tct-buttn\".",
  "code": "ERR_UNKNOWN_COMPONENT",
  "suggestions": [{"name": "tct-button", "reason": "similar name"}]
}
```

A small module in the CLI package (`@tecton-wc/cli/json`, with `parseResponse`, `isError` and `assertResponse`) parses and narrows responses in TypeScript. The envelope and the error-code table are in the [CLI reference](../cli/#json-output).

## MCP server

The CLI ships a Model Context Protocol (MCP) server that any MCP-compatible AI tool can connect to. Instead of pasting CLI output, the AI queries the design system directly: searching for elements, reading full documentation and pulling code examples on demand. It exposes two tools:

- `search(query)` discovers elements, controllers and doc topics with a ranked, keyword-based index, and returns brief results that are aware of compound and related elements.
- `get(name)` retrieves the full documentation for one element, controller or topic, with attributes, slots, events, usage and showcase examples. For a large guide, `get("styling", {section: "parts"})` returns one section.

`tct mcp` runs it over stdio, offline, from the same registry as every other command. The stdio form works with any MCP-compatible tool: Claude Desktop (`claude_desktop_config.json`), Cursor (`.cursor/mcp.json`), Windsurf (`.windsurf/mcp.json`), Cline and others.

```json title="MCP config (stdio)"
{
  "mcpServers": {
    "tecton": {
      "command": "npx",
      "args": ["--no-install", "tct", "mcp"]
    }
  }
}
```

A search and a get, as a client sees them:

```text
search("confirm before deleting")
-> [{"type":"component","name":"tct-alert-dialog","category":"Overlay",
     "description":"modal confirmation for destructive or irreversible actions ...",
     "import":"import '@tecton-wc/components/alert-dialog';",
     "keyAttributes":["open: boolean","action-variant: primary|secondary|ghost|destructive|outlined|text-only"],
     "relatedComponents":["tct-dialog","tct-popover","tct-toast","tct-banner"],
     "hint":"Use get(\"tct-alert-dialog\") for the full API, usage and examples."}, ...]

get("tct-alert-dialog")
-> {"name":"tct-alert-dialog","import":"import '@tecton-wc/components/alert-dialog';",
    "usage":"AlertDialog asks the user to confirm a destructive or irreversible action ...",
    "bestPractices":[...], "elements":[{"attributes":[...],"slots":[...],"events":[...]}],
    "example":{...}, "related":[...], "docs":"/components/overlay/alert-dialog/"}
```

Results are capped (a brief is at most about 6,000 characters), and a large guide comes back as an overview with its section list.

### Live over HTTP: `/mcp`

The docs site also serves the same two tools over HTTP, for clients that connect to a URL instead of starting a process. `GET /mcp` is a server card that names the tools and says how to connect; `POST /mcp` speaks MCP (JSON-RPC 2.0, the Streamable HTTP transport in its stateless, JSON-response form). It answers from the registry the site publishes, so it says exactly what `tct mcp` says.

```json title="MCP config (HTTP)"
{
  "mcpServers": {
    "tecton": {
      "type": "url",
      "url": "https://docs.example.com/mcp"
    }
  }
}
```

There is no public docs site yet (the library is unlicensed and unpublished), so the URL is the one where you host the docs build, and `http://localhost:4321/mcp` while you run it yourself (see below). A round trip against a running server, with `curl`:

```bash title="Ask the server what it offers"
curl -s http://localhost:4321/mcp
```

```json
{
  "name": "tecton-wc",
  "version": "0.0.0",
  "transport": "streamable-http (stateless, JSON responses)",
  "usage": "POST JSON-RPC 2.0 messages to this URL (initialize, tools/list, tools/call).",
  "tools": [
    {"name": "search", "description": "Search the Tecton Web Components: finds elements (tct-*), controllers and utilities, and documentation topics. ..."},
    {"name": "get", "description": "Get full documentation for one element, controller or doc topic by name. ..."}
  ]
}
```

```bash title="initialize, then search"
curl -s -X POST http://localhost:4321/mcp \
  -H 'content-type: application/json' -H 'accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"curl","version":"1"}}}'
```

```json
{"result":{"protocolVersion":"2025-06-18","capabilities":{"tools":{}},"serverInfo":{"name":"tecton-wc","version":"0.0.0"},"instructions":"Search and read the Tecton Web Components docs before writing UI: search(query) finds elements, controllers and guides; get(name) returns the full API, usage and examples. Never invent attributes, slots or events."},"jsonrpc":"2.0","id":1}
```

```bash
curl -s -X POST http://localhost:4321/mcp \
  -H 'content-type: application/json' -H 'accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"search","arguments":{"query":"confirm before deleting","limit":1}}}'
```

```json
{"result":{"content":[{"type":"text","text":"[{\"type\":\"component\",\"name\":\"tct-alert-dialog\",\"displayName\":\"Alert Dialog\",\"category\":\"Overlay\",\"description\":\"modal confirmation for destructive or irreversible actions (delete, revoke access, discard changes); ...\",\"import\":\"import '@tecton-wc/components/alert-dialog';\",\"keyAttributes\":[\"open: boolean\",\"action-variant: primary|secondary|ghost|destructive|outlined|text-only\"],\"relatedComponents\":[\"tct-dialog\",\"tct-popover\",\"tct-toast\",\"tct-banner\"],\"hint\":\"Use get(\\\"tct-alert-dialog\\\") for the full API, usage and examples.\"}]"}]},"jsonrpc":"2.0","id":2}
```

A name that is not exact is not an error: `get("tct-buttn")` answers with the closest matches, and a name with nothing close comes back with `isError: true` and a hint to use `search`.

```json title="Response to get(tct-buttn)"
{"result":{"content":[{"type":"text","text":"{\"note\":\"\\\"tct-buttn\\\" is not an exact name. Did you mean one of these?\",\"suggestions\":[{\"type\":\"component\",\"name\":\"tct-button\",\"description\":\"action trigger w/ 6 variants, 3 sizes, loading state, link + form submitter modes\",\"import\":\"@tecton-wc/components/button\"}],\"hint\":\"Use get() with the exact name from the suggestions above.\"}"}]},"jsonrpc":"2.0","id":3}
```

The endpoint is stateless: every POST gets a fresh server and answers as one JSON document, with no session and no event stream, so a client needs no sticky routing and any number of instances can sit behind a load balancer. Only `GET` (the card) and `POST` are accepted.

### How the docs are served

The site is prerendered: `pnpm docs:build` writes the pages, assets, `llms.txt`, the registry and the search index to `apps/docs/dist/client/`. Only `/mcp` renders on demand, so the build also writes a small Node server (the Astro Node adapter, standalone mode) to `apps/docs/dist/server/entry.mjs`. There are two ways to run it:

- **One Node process for everything.** `node apps/docs/dist/server/entry.mjs` serves the static files from `dist/client/` and answers `/mcp`. Set `HOST` (for example `0.0.0.0` in a container) and `PORT` (default `4321`).
- **A static host for the pages, plus a Node process for `/mcp`.** Publish `dist/client/` on any static host, run the same `entry.mjs`, and route `/mcp` to it (a reverse-proxy rule, or a rewrite on the host). A static host alone cannot answer the POST, so without the Node process `/mcp` does not exist there and clients should use `tct mcp` instead.

```bash title="Build and run the whole site, /mcp included"
pnpm docs:build
HOST=0.0.0.0 PORT=4321 node apps/docs/dist/server/entry.mjs
# [@astrojs/node] Server listening on http://0.0.0.0:4321
```

`pnpm docs:mcp` runs this against the build (the server on a free port, the MCP SDK's client over HTTP, then the card), and `pnpm check` runs it after `docs:build`. The route itself is `apps/docs/src/pages/mcp.ts`: it mounts the CLI's handler, so a site of your own can do the same:

```ts title="src/pages/mcp.ts (a site with a server adapter)"
import {handleMcpRequest} from '@tecton-wc/cli/mcp/http.js';
import registry from '../../public/agent-registry.json';

export const prerender = false;
export const ALL = ({request}: {request: Request}) => handleMcpRequest(registry, request);
```

## `llms.txt` and reference output

For tools that read the web rather than call a CLI, the docs site publishes [llms.txt](/llms.txt) (the [llmstxt.org](https://llmstxt.org) convention) and [llms-full.txt](/llms-full.txt), plus the JSON [registry](/agent-registry.json), all generated from the Custom Elements Manifest and the docs so they cannot drift from the API. `llms.txt` is a short index of the guides and elements; `llms-full.txt` also lists the controllers and utilities. A Markdown reference output is _planned_.
