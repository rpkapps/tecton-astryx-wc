## Overview

`tct` is the primary interface for working with the design system from a terminal, for people and for machines: element documentation, docs topics, agent-context generation, layout tools and an MCP server, through terminal commands, a typed JSON API or programmatic imports. It lives in the private `@tecton-wc/cli` package and reads one generated agent registry (the Custom Elements Manifest, the docs frontmatter with `keywords`, `dense` and `related`, the examples, the tokens, the controllers and the docs topics). The registry is published as [agent-registry.json](/agent-registry.json) and exported as `@tecton-wc/components/agent-registry.json`. The docs site and the MCP server read the same registry, so the surfaces cannot disagree.

```bash
tct --help
tct search dialog
tct component tct-dialog
tct docs tokens
```

The CLI needs Node.js 22.18 or later. It finds the registry in this order: `--registry <file>`, `$TCT_AGENT_REGISTRY`, the `@tecton-wc/components` installed for your project, the workspace copy, then the copy it depends on. So the answers match the version your project runs. Add an npm script alias (`"tct": "tct"`) so that scripts and agents use one stable command, and see [Working with AI](../working-with-ai/#the-tct-pattern) for why.

## Commands

| Command                  | What it does                                                                                                                                                                  |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `component [name]`       | With no name, lists elements by category (`--list`, `--category`). With a name, prints its docs; `--props`, `--example <id>`, `--examples`, `--styling` and `--source` narrow it |
| `docs [topic] [section]` | With no topic, lists the guides (every page in these guides). With a topic, prints it (`--index` lists its sections); with a section, prints just that section                  |
| `search <query...>`      | Searches elements, controllers and docs in one ranked list, tagged with the follow-up command to run (`--type component\|controller\|doc`, `--limit`, `--verbose`)              |
| `discover [query]`       | Lists the library and every installed package that ships an agent registry; browses one package or one of its elements                                                         |
| `controllers [name]`     | Lists the runtime controllers and utilities of `@tecton-wc/core` (the counterpart of the React hooks) or prints one (`--category`, `--members`)                                  |
| `doctor`                 | Diagnoses a project's setup: Node, registry, packages, stylesheet, unknown `tct-*` tags and the freshness of the agent docs. Read-only                                          |
| `gap-report [element]`   | Routes a design-system gap (a missing element, variant, layout or docs page) to the package that owns it (`--category`, `--reason`, `--list-categories`)                        |
| `layout`                 | `layout grammar` prints the grammar, `layout check` validates an expression, `layout expand` produces `tct-*` markup                                                            |
| `init --features agents` | Generates agent context: `--agent claude\|cursor\|codex\|all`, `--agent-docs-path <file>`, `--dry-run` and `--remove-agents`                                                    |
| `upgrade`                | Detects a stale generated agent-docs block. `--apply` refreshes it without touching your own edits; `--check` is a CI gate                                                      |
| `mcp`                    | Starts the MCP server over stdio, exposing `search(query)` and `get(name)`                                                                                                       |
| `manifest`               | Prints the whole CLI surface (commands, options, examples, exit codes, response types) as one JSON document                                                                      |

Text output is a set of aligned `key: value` records separated by a blank line, so a field can be grepped (`tct search button | grep "^command:"`). A search result:

```text
$ tct search dialog --limit 2
Results for "dialog" (2 of 50)

name:        tct-dialog
domain:      component
category:    Overlay
import:      @tecton-wc/components/dialog
description: modal overlay on native dialog that blocks page interaction until the user responds; purposes, nesting, focus return, openDialog()
command:     tct component tct-dialog

name:        tct-alert-dialog
domain:      component
category:    Overlay
import:      @tecton-wc/components/alert-dialog
description: modal confirmation for destructive or irreversible actions (delete, revoke access, discard changes); ...
command:     tct component tct-alert-dialog
```

Search ranks a name match above a keyword match above a mention in prose, understands typos and synonyms ("modal", "popup" and "confirm" all reach the dialogs), and puts a whole-phrase match first. `tct <command> --help` documents one command in full; `tct help <command>` is the same.

### Layout expressions

`tct layout` is a compressed way to write layouts that expands to validated `tct-*` markup, so an agent writes a line instead of a page and cannot invent an element or attribute. `tct layout grammar` prints the cheatsheet for the installed version, including the aliases (`V` is `tct-vstack`, `H` is `tct-hstack`, `B` is `tct-button`, `Tx` is `tct-text`, and so on; tags and short names are always valid). Expressions have a compact form and an outline form (indentation is nesting); the form is detected, or forced with `--form`.

```text
$ tct layout check 'V[gap=4] > (Tx"Title" + H[gap=2] > (B.primary"Save" + B"Cancel"))'
[ok] Valid (parsed as compact)

compact

V[gap=4] > (Tx"Title" + H[gap=2] > (B.primary"Save" + B"Cancel"))

outline

V gap=4
  Tx "Title"
  H gap=2
    B.primary "Save"
    B "Cancel"
```

```html
<!-- $ tct layout expand 'V[gap=4] > (Tx"Title" + H[gap=2] > (B.primary"Save" + B"Cancel"))' -->
<tct-vstack gap="4">
  <tct-text>Title</tct-text>
  <tct-hstack gap="2">
    <tct-button variant="primary" label="Save"></tct-button>
    <tct-button label="Cancel"></tct-button>
  </tct-hstack>
</tct-vstack>

<script type="module">
  import '@tecton-wc/components/button';
  import '@tecton-wc/components/hstack';
  import '@tecton-wc/components/text';
  import '@tecton-wc/components/vstack';
</script>
```

A mistake is reported with its line and column and the closest valid names, and nothing is guessed:

```text
$ tct layout check 'V > (Tx"Title" + Btnn"Save")'
[fail] Invalid (1 error):

- line 1: Unknown element or alias 'Btnn'
  did you mean: Bn?
```

`layout expand` takes the expression as an argument, from a file (`--file`) or from standard input (`-`); an optional path writes the markup there and refuses to overwrite an existing file without `--force`. A trigger with `opens=#id` gets a `data-opens` attribute and a small wiring script that opens the overlay, `fill` on a stack child wraps it in `tct-stack-item`, and repeats (`*N`) and elements are capped so a mistyped count cannot exhaust memory.

### Agent docs

`init` and `upgrade` manage a block of generated text between `<!-- TCT:START -->` and `<!-- TCT:END -->` markers. The block records a hash of its own body, which gives each file a state: `current`, `stale` (an unedited older block), `edited` (someone changed the body; skipped unless `--force`) or `malformed` (duplicate or unterminated markers; reported for repair, never guessed at). Text outside the markers is never read as part of the block and never rewritten. See [Working with AI](../working-with-ai/#quick-start) for the workflow.

### Not in the first release

The commands beyond agent support (`theme` for building and exporting themes, `build`, `swizzle`, `integration` and `blog`) are tracked as a follow-up, and the templates library is deferred, so `template` and the template steps of the agent workflow are too. `gap-report` never files anything publicly (the library is unpublished): it names the owning package and where the request is recorded, and `--output <file>` appends the report to a file in your project. See [CLI Integrations](../cli-integrations/).

## Global options

| Flag                             | Effect                                                                                                                                                  |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--dense`                        | Compressed, token-efficient output for AI context windows. Built from each element's authored dense doc, and complete with respect to its public API     |
| `--json`                         | Output as a stable, typed JSON envelope. Rejected up front by a command that has no JSON form (`mcp`)                                                   |
| `--detail <brief\|compact\|full>` | For list views and docs: names only, names with one-line descriptions, or full docs per entry                                                           |
| `--registry <file>`              | Read this agent registry instead of the installed one (also `$TCT_AGENT_REGISTRY`)                                                                      |
| `-h`, `--help`, `-V`, `--version` | Help for a command, and the version. Both exit 0                                                                                                        |

## JSON output

Every command that prints data supports `--json`. Responses are typed envelopes: an `apiVersion`, a `type` naming the shape of `data`, the `data` itself and an optional `meta`:

```json
{"apiVersion": 1, "type": "search", "data": {"query": "dialog", "matchCount": 50, "results": ["..."]}}
```

The types are `component.list`, `component.detail` (and `.props`, `.examples`, `.styling`, `.source`), `docs.list`, `docs.detail`, `docs.index`, `docs.detail.section`, `search`, `discover.list`, `discover.detail`, `discover.detail.doc`, `discover.search`, `controller.list`, `controller.detail`, `controller.detail.members`, `doctor`, `gap-report.categories`, `gap-report.file`, `layout.grammar`, `layout.check`, `layout.expand`, `init.run`, `init.remove`, `upgrade.run` and `manifest`. `tct manifest --json` lists them per command. `--dense --json` returns a reduced projection and marks it with `meta.dense`.

Errors carry a stable machine-readable `code`:

```json
{
  "apiVersion": 1,
  "error": "No element named \"tct-buttn\".",
  "code": "ERR_UNKNOWN_COMPONENT",
  "suggestions": [{"name": "tct-button", "reason": "similar name"}]
}
```

The `code` is a stable identifier. Branch on it, never on the human-readable `error` string, which changes freely as the wording improves. Every error envelope has a `code` (`ERR_UNKNOWN` when no specific one applies). Codes are append-only: once shipped, a code's meaning never changes and it is never removed.

| Group               | Codes                                                                                                                                                                                                           |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Parsing             | `ERR_UNKNOWN_COMMAND`, `ERR_UNKNOWN_SUBCOMMAND`, `ERR_INVALID_OPTION`, `ERR_INVALID_ARGUMENT`, `ERR_MISSING_ARGUMENT`, `ERR_INVALID_DETAIL`                                                                       |
| Environment         | `ERR_NODE_VERSION`, `ERR_REGISTRY_NOT_FOUND`, `ERR_REGISTRY_INCOMPATIBLE`                                                                                                                                         |
| Lookups             | `ERR_UNKNOWN_COMPONENT`, `ERR_UNKNOWN_CONTROLLER`, `ERR_UNKNOWN_TOPIC`, `ERR_UNKNOWN_SECTION`, `ERR_UNKNOWN_CATEGORY`, `ERR_UNKNOWN_PACKAGE`, `ERR_UNKNOWN_AGENT`, `ERR_UNKNOWN_FEATURE`, `ERR_NOT_FOUND`, `ERR_AMBIGUOUS_COMPONENT` |
| Missing artifacts   | `ERR_NO_DOC`, `ERR_NO_SOURCE`, `ERR_NO_EXAMPLE`                                                                                                                                                                   |
| Files               | `ERR_FILE_NOT_FOUND`, `ERR_FILE_EXISTS`, `ERR_PATH_TRAVERSAL`, `ERR_WRITE_FAILED`                                                                                                                                 |
| Agent docs, layout  | `ERR_AGENT_DOCS_MALFORMED`, `ERR_LAYOUT_PARSE`, `ERR_LAYOUT_INVALID`                                                                                                                                              |
| MCP                 | `ERR_MCP`                                                                                                                                                                                                       |

The CLI package exports a small module for consuming responses in TypeScript:

```ts
import {parseResponse, isError, assertResponse} from '@tecton-wc/cli/json';

const result = parseResponse(raw);
if (isError(result)) {
  switch (result.code) {
    case 'ERR_UNKNOWN_COMPONENT':
      // suggest the closest match from result.suggestions
      break;
    default:
      console.error(result.error);
  }
}
```

## Exit codes

A command exits with `0` on success and `1` on any error, for a `--json` run as for a text run. Help and version exit `0`. In `--json` mode standard error stays empty and the error is the envelope on standard output. Two commands also use the exit code as a verdict: `layout check` exits 1 for an invalid expression, and `upgrade --check` exits 1 when a block is stale, edited or malformed. The contract tests check exit codes, the JSON contract, the dense projection, `init` behaviour, the protection of files you have edited during `upgrade`, and MCP search and get.

## Programmatic use

The commands are importable, so build tools and agents can call them without spawning a process. `execute` runs a command in-process and returns what it printed:

```ts
import {execute} from '@tecton-wc/cli';
import {assertResponse} from '@tecton-wc/cli/json';

const {exitCode, stdout} = await execute(['component', 'tct-dialog', '--json'], {cwd: process.cwd()});
const {data} = assertResponse(stdout, 'component.detail');
```

The package also exports `search`, `loadRegistry`, `RegistryLookup`, `mcpSearch`, `mcpGet` and `createMcpServer` (the pure functions behind the MCP tools and the server itself), and `handleMcpRequest` (the same server as a `Request` to `Response` handler). This is also how an agent-eval harness drives the CLI: `execute` needs no subprocess and takes the working directory and environment as arguments.
