## Overview

Treat migration as a product-shell and workflow migration, not a global class replacement. Start by loading the theme and putting the app inside the shell, then move one route or surface at a time to elements, keeping existing data, routing and business logic intact.

Tailwind can coexist during migration. Use it for legacy wrappers and local layout, while replacing interactive controls, navigation, command surfaces, forms, alerts, dialogs and settings UI with elements. Because the elements do not depend on your framework, you can also migrate framework by framework, or leave the app framework alone and change only the components.

## Recommended order

1. Install the packages and load the theme stylesheet, so the project has tokens and (optionally) fonts. Run `tct init --features agents` (_planned_) to add agent docs.
2. Pick the initial colour mode behaviour: follow the system by default, and add a mode switch later if you need one (see [Theming](../theme/#light-and-dark-mode)).
3. Make the layer order of your CSS explicit before replacing components.
4. Render the foundation smoke test page and confirm tokens and light-DOM elements keep their styles before migrating any surface.
5. Move the persistent frame first: `tct-app-shell`, `tct-top-nav`, `tct-side-nav`, page content and mobile navigation (all _planned_).
6. Replace shared primitives: `tct-button`, `tct-icon-button`, `tct-text-input`, `tct-dialog`, `tct-alert-dialog`, `tct-banner`, toasts, `tct-badge`, `tct-card` and `tct-list-item` are available; `tct-number-input`, `tct-switch`, `tct-checkbox-input`, `tct-radio-list`, `tct-selector`, `tct-tab-list` and `tct-table` are _planned_.
7. Replace global workflows: the command palette, the settings popover, the theme toggle, search, filters, create flows and destructive confirmation dialogs.
8. Remove legacy Tailwind classes from each completed surface, keeping only token-backed layout utilities and local wrappers that still await migration.
9. Verify both colour modes, keyboard navigation, responsive layout, and empty, error and loading states before moving to the next route.

## Theme and CSS setup

Load the stylesheet once, in the document, so every migrated element reads the same token set. If users can switch between light and dark, keep the choice in application state, apply it to `<html data-theme>` (or a `tct-theme`) and persist it.

```html title="index.html"
<meta name="color-scheme" content="light dark" />
<link rel="stylesheet" href="/vendor/tecton-wc/tecton.css" />
<script type="module">
  import '@tecton-wc/components/button';
</script>
```

When Tailwind remains in the app, declare the layer order once in the global CSS file. The theme and the tokens should load before Tailwind's utilities, so migrated elements keep their defaults while legacy utility classes still work.

```css title="Tailwind v4 coexistence"
@layer theme, base, tecton.reset, tecton.tokens, tecton.light-dom, components, utilities;

@import 'tailwindcss/theme.css' layer(theme);
@import 'tailwindcss/preflight.css' layer(base);
@import '@tecton-wc/tokens/tecton.css';
@import 'tailwindcss/utilities.css' layer(utilities);
```

On Tailwind v3 there is no `preflight.css` to import, so wrap the `@tailwind base` directive in a named layer instead. Keep utilities unlayered so existing app utility classes still win everywhere.

```css title="Tailwind v3 coexistence"
@layer tw-preflight, tecton.reset, tecton.tokens, tecton.light-dom;

@import '@tecton-wc/tokens/tecton.css';

@layer tw-preflight {
  @tailwind base; /* layered: the tokens now win over preflight */
}
@tailwind components;
@tailwind utilities; /* unlayered: legacy utility classes keep winning */
```

## Cascade layer safety

In a stylesheet with no layers at all, a zero-specificity reset like `* { padding: 0 }` loses to any class selector, so most developers treat resets as harmless. Layers change the rules twice: unlayered styles beat every named layer, and a later layer beats an earlier one, both regardless of specificity. The same reset therefore wins against a layered style either by staying unlayered or by landing in a layer declared later.

The exposure is smaller for elements than for a library that renders into your DOM. Selectors in your page (including `*`) do not reach inside a shadow root, so a legacy reset cannot flatten the internals of `tct-button`, `tct-text-input` or `tct-dialog`. Three things can still be hit, and they are worth an audit:

- **Light-DOM elements.** Elements that render into your DOM are styled by `@layer tecton.light-dom`: the providers (`tct-theme`, `tct-size-provider` and the others) today, and `tct-table` and `tct-markdown` (_planned_) later. An unlayered legacy reset such as `* { padding: 0 }` or `table { border-collapse: collapse }` beats those layered styles silently.
- **The host boxes.** Rules in your page beat an element's own `:host` rules. A reset that changes `display` or `margin` for arbitrary elements changes the element's layout box.
- **Token names.** Tokens are unprefixed custom properties on the document. A legacy stylesheet that declares the same names (Tailwind's `--font-weight-*`, or an old shadcn theme) competes with them by layer order.

This is the most common way an adoption breaks, through one of two `@import` mechanisms. A top-level `@import` without the `layer()` keyword keeps the legacy stylesheet unlayered, where it overrides every layer. And an `@import` nested inside a file that was itself imported into a layer inherits that surrounding layer, so a reset can silently land in a layer above the theme's. Either way the fix is the same: import the legacy stylesheet into the lowest layer explicitly.

```css title="Legacy reset, explicitly layered"
/* was: @import './legacy-reset.css';  (unlayered: beats every layer) */
@import './legacy-reset.css' layer(reset);
```

Audit the layers around the theme with this checklist before building screens:

- Declare the canonical `@layer` order once, before any `@import`. With webpack-based bundlers, including Next.js, the order declaration must live in its own CSS file imported first, such as `layers.css`, because webpack hoists `@import` content above the inline CSS that follows it.
- Audit every pre-existing global or reset stylesheet and assign each one to a layer on purpose. Top-level imports without `layer()` stay unlayered and beat every layer; imports nested inside a layered file inherit that layer.
- Remove or demote the app's legacy reset. The theme stylesheet declares its layers as `tecton.reset, tecton.tokens, tecton.light-dom`, and an app reset belongs below them, never above.
- Layer Tailwind's preflight. On Tailwind v4, import `preflight.css` with `layer(base)`. On Tailwind v3, wrap the `@tailwind base` directive in a named layer. Unlayered preflight overrides the light-DOM styles silently.
- Set `moduleResolution` to `bundler` or `node16` and newer so package subpaths such as `@tecton-wc/components/button` resolve in TypeScript.
- Theme with token overrides rather than hand-editing a copy of the stylesheet. Keep `--color-on-accent` consistent with any `--color-accent` you change: the pair is designed for contrast, and changing one leaves the other at a stale value.
- Run the foundation smoke test below and view a few elements in both colour modes before migrating any route.

One more mental model shift: a `class` or utility class you put on an element reaches the host in the DOM either way, but whether it overrides an element's own host styles is a cascade question, not a source-order question. Keep app utilities in the utilities layer so that they keep winning.

## Foundation smoke test

A broken layer order can fail silently and identically on every page, so catch it before feature work instead of after several migrated screens. Render one throwaway page with a few elements as the first migration step.

<Example
  title="Foundation check page"
  description="A primary button, a text input and a card. When the foundation is sound the button has visible padding and a filled primary background, and the input and card have borders and internal spacing."
  source={`<tct-vstack gap="4" h-align="start">
  <tct-button variant="primary" label="Primary action"></tct-button>
  <tct-text-input label="Email" placeholder="you@example.com"></tct-text-input>
  <tct-card padding="4"><tct-text>One card with default padding</tct-text></tct-card>
</tct-vstack>`}
/>

If the button has visible padding and a filled primary background, and the input and card have borders and internal spacing, the foundation is sound. Wrap the page in `tct-theme` (a light-DOM element) to check the layered styles too. For an assertion that can run in any test runner or a development-only script, check that the tokens are present and that the light-DOM island has kept its box:

```js title="Foundation assertion"
const root = getComputedStyle(document.documentElement);
if (!root.getPropertyValue('--color-accent').trim()) {
  throw new Error('Foundation broken: tokens.css is not loaded (or is overridden by a later declaration).');
}

const island = document.querySelector('tct-theme');
if (!island) {
  throw new Error('Foundation check page did not render a tct-theme.');
}
if (getComputedStyle(island).display !== 'block') {
  throw new Error(
    'Foundation broken: an unlayered reset or a later cascade layer is overriding light-DOM ' +
      'element styles. Check that no app reset sits outside the reset layer.',
  );
}
```

When this fails, the fix is almost always in the layer order: find the stylesheet that overrides `display` or zeroes padding, and move it into the reset layer or delete it.

## Move the app frame first

Start with `tct-app-shell` so page migration happens inside the final navigation, spacing, surface and responsive frame. This also exposes theme and colour issues early, because every route shares the same shell. The shell, navigation and layout elements are _planned_; until they ship, keep your current frame and move the content inside it.

| Legacy surface      | Element                                              | Notes                                                                                            |
| ------------------- | ---------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| Header              | `tct-top-nav` (_planned_)                            | Product identity, global actions, account entry, and the command or search trigger.              |
| Sidebar             | `tct-side-nav` (_planned_)                           | Sections and nested items for route groups. Keep selection state driven by the router.           |
| Main page wrapper   | `tct-app-shell` and `tct-layout` (_planned_)         | Let the shell own persistent structure; let route components own page content.                   |
| Mobile drawer nav   | `tct-mobile-nav` (_planned_), or the shell's mobile behaviour | Verify focus, close behaviour and route changes on narrow viewports.                    |
| Settings menu       | `tct-popover` and a toggle control                   | The home for theme mode and app preferences.                                                     |

Wire routing through `tct-link-provider`, so every `tct-link`, navigation item and breadcrumb uses your router instead of doing a full page load.

## Map shadcn and Radix primitives

Do not wrap old shadcn components in the new styles. Replace the primitive with the element that owns the behaviour, accessibility, state and token usage.

| Existing primitive         | Element                                    | Migration note                                                                                           |
| -------------------------- | ------------------------------------------ | -------------------------------------------------------------------------------------------------------- |
| `button` / shadcn Button   | `tct-button` or `tct-icon-button`          | `tct-button` for labelled commands and `tct-icon-button` for icon-only toolbar actions.                  |
| `input`                    | `tct-text-input`                           | Keep validation state in the element's status and validation, not in ad hoc border classes.              |
| `textarea`                 | `tct-text-area` (_planned_)                | When multi-line editing is the primary action.                                                           |
| `switch`                   | `tct-switch` (_planned_)                   | For persisted boolean settings, including theme mode when it is a binary choice. `tct-toggle-button` is available for a pressed or released action. |
| `checkbox`                 | `tct-checkbox-input` or `tct-checkbox-list` (_planned_) | Use the list for grouped selection.                                                         |
| `radio group`              | `tct-radio-list` (_planned_)               | When exactly one option must be selected from a visible set. `tct-segmented-control` is available for a small set. |
| `select` / combobox        | `tct-selector` or `tct-typeahead` (_planned_) | `tct-selector` for bounded options, `tct-typeahead` for searchable or async options.                  |
| `tabs` used as page nav    | `tct-tab-list` (_planned_)                 | Use route state or current-page state as the source of truth.                                            |
| `command` dialog           | `tct-command-palette` (_planned_)          | Keep app-specific search sources outside the shell and feed searchable items.                            |
| `dropdown-menu`            | `tct-dropdown-menu` or `tct-more-menu` (_planned_) | `tct-more-menu` for compact overflow actions.                                                    |
| `alert` / callout          | `tct-banner` or a toast                    | A banner for page or section messages, a toast (the imperative `toast()` function) for transient feedback. |
| `dialog`                   | `tct-dialog` or `tct-alert-dialog`         | `tct-alert-dialog` for destructive confirmation and `tct-dialog` for task flows.                         |
| card-like list row         | `tct-list-item`                            | Prefer it for selectable rows instead of styling a button as a row.                                      |

Radix primitives are behaviour without style, and the elements ship the behaviour: keyboard contracts, focus return, layer stacking and dismissal come built in. Delete the wiring you wrote around Radix (portals, focus-scope, dismissable-layer) instead of porting it.

## Command palette, settings and theme

Move global search to `tct-command-palette` (_planned_) once the shell exists. Treat the palette as a view over app commands: routes, contextual actions, create actions, filters, recent items and entity results. Keep data normalisation in app code, so that search sources always return arrays of searchable items.

Put light and dark mode controls in the settings popover or the account menu. The control should set the mode on `<html data-theme>` (or on the outermost `tct-theme`), not toggle isolated body classes.

```html title="Settings popover theme control"
<tct-toggle-button id="dark-mode" label="Dark mode"></tct-toggle-button>

<script type="module">
  const toggle = document.querySelector('#dark-mode');
  toggle.pressed = document.documentElement.dataset.theme === 'dark';
  toggle.addEventListener('tct-pressed-change', (event) => {
    document.documentElement.dataset.theme = event.pressed ? 'dark' : 'light';
  });
</script>
```

A binary control pins a scheme once it has been chosen; the [theming guide](../theme/#light-and-dark-mode) describes the two-state control that keeps "follow the system" as the default.

## Verification checklist

- Run the app in light and dark mode and check that surfaces, borders, text, icons, hover states, focus rings and status colours flow together.
- Open the command palette from the shell, type into it, select items by keyboard, and confirm focus returns to the trigger (once the palette ships).
- Check the side navigation collapsed, expanded, active, hovered, nested and on mobile (once it ships).
- Verify settings popovers and dialogs in a real browser. The native `<dialog>` and [`Popover`](https://developer.mozilla.org/en-US/docs/Web/API/Popover_API) APIs may not exist, or may behave differently, in a DOM emulation such as jsdom; run browser-level tests for these.
- Search for leftover hardcoded Tailwind colours, arbitrary hex values and one-off hover colours after each route migration.
- Run component tests, the build, and at least one browser screenshot pass for each migrated route.
