Shadow DOM is a style boundary. Page rules do not reach into an element, and an element's own rules do not leak out. Only inherited properties cross it, and that includes CSS custom properties. Everything on this page is a deliberate way across the boundary, in the order you should reach for it.

## Overview

There are several ways to style things. Here is when to use each:

| Approach                       | Use for                                                                       | Example                                                        |
| ------------------------------ | ----------------------------------------------------------------------------- | -------------------------------------------------------------- |
| Design tokens                  | Theming a whole page or subtree; the first thing to try                        | `.settings { --color-background-surface: var(--color-background-muted); }` |
| Attributes                     | The documented visual axes: variant, size, elevation, width                    | `<tct-button variant="primary" size="sm">`                     |
| `::part()`                     | One anatomy element of one element type, with any property                     | `tct-button::part(button) { text-transform: uppercase; }`      |
| `:state()`                     | Styling on a runtime state the element owns (read-only)                        | `tct-button:state(loading) { … }`                              |
| Component custom properties    | The few knobs an element documents                                             | `tct-button { --button-focus-offset: 3px; }`                   |
| `::slotted()`                  | Small touch-ups to content you slot in                                         | `tct-card ::slotted(img) { … }`                                |
| `class` and `style` on the host | The element's own box in your layout: margin, grid area, flex sizing, width   | `<tct-card class="span-2">`                                    |
| Tailwind utilities             | Page layout and wrappers                                                       | `<div class="flex gap-3 p-4">`                                 |
| Styling-library token aliases  | Keeping Tailwind, Panda, MUI or CSS-in-JS in sync with the tokens              | See [Styling library interop](../styling-libraries/)           |

Every approach resolves to the same design tokens, so theming and dark mode work regardless of which you choose.

## Where `xstyle` and `className` went

Astryx for React gives every component an `xstyle` prop (StyleX styles), a `className` and a `style`. None of those is an API here, and this is a recorded, approved difference. There is no build-time styling library to feed, and a `class` on a custom element only reaches its host box, not the parts inside its shadow root. The replacements are:

| Astryx for React                          | Here                                                                                     |
| ----------------------------------------- | ---------------------------------------------------------------------------------------- |
| `xstyle` (StyleX overrides)               | A rule in your stylesheet that targets the element: `tct-button::part(button)`, a custom property, or a token |
| `className`                               | The standard `class` attribute on the host. It styles the host box, so use it for layout |
| `style`                                   | The standard `style` attribute on the host, with the same scope as `class`               |
| `data-*`, `aria-*`, `id`, event handlers  | The same attributes and events, on the host                                              |
| `ref`                                     | The element itself is the DOM node; some elements also expose getters such as `control` |

## Design tokens first

Tokens are inherited custom properties. Set one on any ancestor and every element below it follows:

```css
.dense-table {
  --spacing-4: 12px;
  --color-background-surface: var(--color-background-muted);
}
```

Use tokens instead of hardcoded values everywhere in your own CSS too. Tokens are CSS custom properties that adapt to the colour mode. The system provides tokens for colour, spacing, radius, shadow, typography and size:

```css
.summary-panel {
  padding: var(--spacing-4);
  border-radius: var(--radius-container);
  background-color: var(--color-background-surface);
  border: var(--border-width) solid var(--color-border);
}
```

Do not write colour literals (`#fff`, `rgb(…)`) in code that sits next to the elements. They will not adapt to dark mode or to a theme, and they leave the Tecton system. See [All tokens](../tokens/) for every name and value.

## Attributes

An element's visual axes are ordinary attributes. Boolean attributes follow the platform: presence means true, and the value `"false"` is not a thing. The generated element page lists every attribute, its type and its default.

```html
<tct-button variant="primary" size="sm">Save</tct-button>
<tct-card elevation="low">A raised card</tct-card>
<tct-heading level="1" type="display-1">Hero title</tct-heading>
```

Enumerated attributes are validated. An unknown value falls back to the default, and in development (`globalThis.tctDevMode = true`) the element warns once.

## `::part()`: one anatomy element

Elements expose their painted anatomy as parts, one per Astryx theming target (kebab-case, without the component prefix): a button exposes `button`, and a selector exposes parts such as `popup`, `option`, `search` and `clear-icon`. Each element's page lists its parts. Parts accept any CSS property, and rules that you write in the page win over the element's internal layers.

```css
tct-button::part(button) {
  letter-spacing: 0.02em;
}

tct-selector::part(popup) {
  max-block-size: 24rem;
}
```

A composite that embeds another element re-exports that element's parts under qualified names, so the upstream target names survive: for example, the selector's `popup` becomes `selector-popup` on a composite that contains it.

Parts are versioned API. Adding one is a minor change, and removing or renaming one is a major change. Elements only expose a part when the anatomy paints something, so there is no part on a wrapper that paints nothing.

Do not try to style what has no part. If you find yourself wanting `element.shadowRoot.querySelector(…)`, the right move is to ask for a part or a custom property, not to reach in.

## `:state()`: runtime states

Elements expose read-only runtime state through custom states. Style them from your own CSS with the state pseudo-class:

```css
tct-button:state(loading) {
  opacity: 0.8;
}

tct-text-input:state(user-invalid) {
  margin-block-end: var(--spacing-2); /* leave room for the message */
}
```

Common states are `loading`, `open`, `checked`, `user-invalid` and `highlighted`, and slot-presence states such as `has-description`. They are documented per element. A custom state can be styled but not set from outside, which keeps the element the only writer. Two things to remember:

- Custom states are not serialised, so anything needed for first paint on a server-rendered page must be an attribute, not a state.
- `:state()` is present in every Tier 1 engine but may not match in Tier 2. Nothing inside the library depends on it, but your own styles that do will not apply there. See [Browser support](../browser-support/).

## Component custom properties

A small number of properties are documented per element, for the cases where no token or part covers the need. They are named `--<component>-<css-property>` and never per size. `--button-focus-offset` (default 1 px in Tecton) is one.

```css
tct-button {
  --button-focus-offset: 3px;
}
```

Elements do not seed these properties on `:host`. They read them through a private alias that has a token fallback, so you can set a documented property on the element or on any ancestor. Properties that start with an underscore (`--_button-bg`) are private, and they are not an API.

## Slotted content

Content you place in a slot belongs to you, so your own CSS styles it, and it inherits `color` and `font` through the host. `::slotted()` can only reach the top-level slotted nodes and loses to your own rules, which is what you want: use it for light touch-ups only. Never use `!important` to force aesthetics through it.

Rich content that an element renders into the light DOM (tables, Markdown) is styled by a low-priority stylesheet in `@layer tecton.light-dom`. Your ordinary CSS overrides it without extra specificity. To opt a subtree out of those styles, mark it with `data-tct-unstyled`.

## `class`, `style` and the host

The host is a layout box. Use `class` or `style` for the things that place it in your layout: `margin`, `grid-area`, `flex`, `width`, `display`, `align-self`. The painted surface (background, border, padding, radius, shadow, focus ring) lives on an inner part, so style those with `::part()` instead of on the host. A rule on the host paints around the part and can put the radius and the focus ring out of step.

```html
<div class="toolbar">
  <tct-button class="push-end" variant="ghost">Cancel</tct-button>
  <tct-button variant="primary">Save</tct-button>
</div>
```

```css
.toolbar {
  display: flex;
  gap: var(--spacing-2);
}
.push-end {
  margin-inline-start: auto;
}
```

Use logical properties (`margin-inline-start`, `padding-block`, `inset-inline-end`) in your own CSS so that layouts mirror in right-to-left.

## Rest props: attributes and events

Attributes you put on the host stay on the host. `data-*` attributes, `id`, `class`, `lang` and `dir` behave as on any element. ARIA attributes on a host (`aria-label`, `aria-describedby`, `aria-expanded`, and the rest of the delegated set) are forwarded to the element's inner control, and ID references are resolved in your tree, so `aria-describedby="hint"` on `<tct-text-input>` works even though the input lives in a shadow root.

Native events are not renamed. `click`, `input`, `change`, `focus` and `blur` come from the inner control and retarget to the host. Only notifications with no native equivalent are `tct-`prefixed events. Do not add a `role` attribute to an element that already has one; it overrides the role the element sets through `ElementInternals`.

```html
<tct-card data-testid="user-card" data-user-id="42" aria-label="User profile card">…</tct-card>
<script type="module">
  document.querySelector('[data-testid="user-card"]').addEventListener('mouseenter', handleHover);
</script>
```

## Compound elements

Complex elements are composed from smaller ones. Each child is its own element with its own attributes and parts, so you style the pieces individually; there is no single "drill into a sub-part" attribute.

```html
<tct-dialog id="edit-profile" heading="Edit profile" width="500">
  <tct-text-input label="Name" name="name"></tct-text-input>
  <tct-button variant="primary">Save</tct-button>
</tct-dialog>
```

```css
/* the dialog owns structure and behaviour; each child styles itself */
#edit-profile tct-text-input {
  margin-block-end: var(--spacing-3);
}
#edit-profile tct-button::part(button) {
  min-inline-size: 6rem;
}
```

The pattern: the parent element (the dialog) controls structure and behaviour; child elements control their own appearance. Style each piece where it lives.

## Selector surface

When external CSS needs to target an element by property or state, combine the tag name with the reflected attribute. The tag replaces Astryx's stable component class (`.astryx-button`), and the reflected attribute replaces its data attributes:

```css
/* Astryx for React: .my-app .astryx-button[data-variant="primary"][data-size="sm"] */
.my-app tct-button[variant='primary'][size='sm'] {
  /* small primary buttons in this app context */
}

.my-app tct-heading[level='2'] {
  /* level 2 headings; numeric values stay literal in attributes */
}
```

Only the attributes an element reflects are selectable. Reflection is deliberate and limited: `variant`, `size`, `open`, `disabled`, `readonly`, `required`, `orientation`, and `selected` or `checked` only on non-form items such as tabs and options. Anything the element derives at run time is a custom state.

Astryx for React also emits deprecated bare prop and state classes (`.primary`, `.sm`, `.level-2`, `.checked`) during a removal window. They are not emitted here, and there is no rewrite step to run. If you are migrating selectors, use the table above and the [React to Web Components](../react-to-web-components/) guide.

## Cascade layers

Element styles live in cascade layers inside the shadow root, in the fixed order `reset`, `component`, `state`, `a11y`. Layer names inside a shadow root do not interact with your page's layers, and your `::part()` and host rules come from outside, so they win over all of them. That is why you never need `!important`.

For your own page, the theme stylesheet declares `@layer tecton.reset, tecton.tokens, tecton.light-dom;`. If you use Tailwind or other layered CSS, declare the order once, before any `@import`. The recommended order is on the [Installation](../installation/#stylesheets-and-fonts) page.

## Tailwind

Tailwind utilities work well on the layout of the elements themselves and on your own wrappers, and they do not conflict with the theme. Two things to know:

- **Preflight cannot hurt the elements.** Application resets such as Tailwind's preflight can override `:host` rules, so elements keep their paint on inner parts. They render correctly under a preflight.
- **One token collision.** Tailwind v4's default theme defines `--font-weight-normal`, `--font-weight-medium`, `--font-weight-semibold` and `--font-weight-bold`, the same names as the tokens here (which map `semibold` to 500 and `bold` to 600). Put the theme layers above Tailwind's `theme` layer, as in the layer order on the Installation page, so the token values win.

See [Styling library interop](../styling-libraries/) for mapping token names to Tailwind utilities.

## What not to do

**Don't:**

- Put `style="…"` on raw `<div>` wrappers just to add margin. Put `class` or `style` on the element itself.
- Hardcode colours (`#fff`, `rgb(…)`). Use `var(--color-*)` tokens.
- Hardcode spacing (`16px`, `1rem`). Use `var(--spacing-*)` tokens or the element's `gap` and `padding` attributes.
- Use `!important`. If styles are not applying, check whether you are styling the host instead of a part; parts win by design.
- Use `:host-context()` or customised built-ins (`is="…"`). They are not supported, and Firefox and Safari have declined to ship both.
- Set a `border-radius` shorthand on `tct-button` or `tct-toggle-button` parts. Inside a button group the elements square their interior corners with per-corner logical radii, and a shorthand flattens every corner. Use `border-start-start-radius` and its siblings if you must.
- Subclass an element to theme it. It works technically, but it is not a supported or documented path.

## No swizzling, no build step

Astryx's `swizzle` command copies component source into your app, which then needs a build-time StyleX compiler to render. There is nothing to compile here: elements ship as ES modules with their CSS inside, and you need no styling toolchain. The `swizzle` command has no equivalent in the first release. It is tracked with the other non-agent CLI commands as a follow-up.
