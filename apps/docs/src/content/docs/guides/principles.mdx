## Design philosophy

The design system prioritises consistency, adaptability and developer experience. Every decision flows from a few core ideas:

- **Elements over primitives.** Use `tct-*` elements for everything they cover before reaching for raw HTML. Where no element exists, plain semantic HTML is the right tool: headings, lists, paragraphs and links in prose need no wrapper.
- **Semantic tokens over hardcoded values.** Colours, spacing and radii are named by purpose, not appearance (`--color-text-secondary`, `--spacing-4`, `--radius-container`).
- **Theme-agnostic code.** Your app code never references specific colours or measurements, so themes and dark mode work automatically.
- **Open internals.** Every element class, controller and event is exported and composable, so you can build on top of them without fighting them. The runtime that the elements share lives in `@tecton-wc/core`.
- **The platform first.** Native elements inside the shadow root when the element _is_ a native control (a real `<button>`, `<input>`, `<dialog>`), native events, native form participation, native popovers. You inherit the platform's accessibility and behaviour instead of a re-implementation.

## Rules

1. Use elements for everything they cover.
2. Page layout is frame-first: pick the shell and budget regions before writing content (see [Layout](../layout/)).
3. Dense data renders as rows (`tct-list` with `tct-list-item`, or a table, _planned_), edge to edge with dividers. `tct-card` is for widgets, galleries and settings groups.
4. Style through the public styling API: tokens first, then attributes, `::part()`, `:state()`, documented component custom properties, and `::slotted()` for small adjustments (see [Styling components](../styling/)).
5. Semantic tokens, not hardcoded values (see [All tokens](../tokens/)).
6. CSS custom properties for colours, not hex values.
7. Form controls follow the native model: give them a `name`, read and write `value`, listen for `input` and `change`, and let them submit with their form. They own their state by default (uncontrolled). To control one, set the property and listen for the `tct-*-change` intent event; call `preventDefault()` to refuse a change. See [Forms](../forms/).
8. Navigate with real links. Use `tct-link` for internal navigation, and wrap the app in `tct-link-provider` so consumers can plug their router into every link.

## Styling approach

Elements accept the standard `class` and `style` attributes on the host for layout (margins, flex and grid placement, sizing). There is no style-override prop, because there is no styling library to feed. For anything else, use design tokens, the documented attributes, `::part()` selectors and component custom properties.

See [Styling components](../styling/) for the complete guide with examples.

## Anti-patterns

**Don't:**

- Inline styles on raw elements. Use tokens, attributes or parts, or a class in a stylesheet.
- Hardcoded colours (`#fff`). Use `var(--color-*)`, or a Tailwind semantic class that maps to one (see [Styling library interop](../styling-libraries/)).
- Hardcoded spacing (`16px`). Use spacing tokens (`var(--spacing-4)`) or the element's `gap` and `padding` attributes.
- Hardcoded `<a>` elements for in-app navigation. Use `tct-link` so consumers can swap in their router through `tct-link-provider`.
- Wrapping every list item or page section in a card. Decide the frame first; dense data renders as rows (see [Layout](../layout/)).
- Badge as decoration. Reserve `tct-badge` for counts and enumerated states, and use `tct-status-dot` for status.
- Inventing attributes or events. Read the element's documentation first (its page under [Components](/components/), the Custom Elements Manifest, or `tct component` once the CLI ships).
- Setting a `role` attribute on an element that already has one. Elements expose their default role through `ElementInternals`, and a host attribute overrides it.
- Reaching into a shadow root (`element.shadowRoot.querySelector(…)`) to style or script an element. Use `::part()`, custom properties, properties, methods and events; they are the supported, stable surface.
- Listening for framework-style callbacks. There are no `onClick`-style properties: use `addEventListener` (or your framework's custom-event binding).

## Design tokens

The design system provides semantic design tokens for colour, spacing, radius, shadow, typography and size. Tokens adapt to the active colour mode. See [All tokens](../tokens/) for the full reference with values.

## How to read this documentation

Values in these pages carry one of these labels wherever it matters, so you know how much weight they carry:

| Label              | Meaning                                                                                                                                       |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| Tecton             | The value comes from the Tecton design system: its export, or the owner's Tecton theme bindings.                                              |
| Retained default   | Tecton has no value, so the original default is kept on purpose (motion, breakpoints, z-index).                                                |
| Provisional        | No Tecton decision exists yet. The value is a proposal (data-visualisation colours, the 36 px large control height, some pipeline extras).    |
| Planned            | The API or feature is specified but is not available yet. Do not build on it until its page says it exists.                                   |

The [design tokens reference](/reference/tokens/) shows the status of every token, and the [Components](/components/) overview shows which elements exist.
